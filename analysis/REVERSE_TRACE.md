## 0. Ключ к «мусору» в декомпиле: INT-обёртки эмулятора x87

Оба декомпила завалены `swi()`-вызовами. Причина установлена по байтам: код MS FORTRAN 5.0
компилирован под **эмулируемый x87** — каждая команда сопроцессора обёрнута софт-прерыванием
из диапазона INT 34h–3Eh (обработчики ставит внешний рантайм/TSR-эмулятор, сам EXE их не
ставит). Статистика по всему бинарнику: за `CD 3C` следуют ESC-байты x87 (D8..DF) — 700+ чистых
пар (D9×346, DD×251, DC×64, D8×56), перед LES/MOV-загрузками адресов стоит `CD 3D`.

Модель чтения, использованная ниже:

| Байты | Смысл |
|---|---|
| `CD 3C` + `ESC modrm…` | одна команда x87 с операндом в памяти (FLD/FMUL/FADD/FDIV/FSTP…) |
| `CD 38`…`CD 3B` | другие формы x87-обёрток (в т.ч. деления и проверки статуса) |
| `9E` (SAHF) после записи статуса в AH | тест x87-условия (аналог FSTSW AX/SAHF/Jcc) |
| `CD 35` + `OUT DX,AL` | вывод/диагностика эмулятора |

Ghidra этого не знает, поэтому превратил обёртки в `swi()`-кашу и «склеил» хвосты соседних
функций: тело трейсера разрезано на куски с метками `LAB_1000_0c72…LAB_1000_12cb`
(linear `0x10c72…0x112cb`) — общий хвост, к которому прыгают и f344, и оркестратор
`FUN_1000_cf98`. Именно там сосредоточена FP-математика (FP-hotspot окна 0x10c72–0x112d0).

### 0.1. Уточнение модели (TASK_REVERSE3, побайтовая проверка шести новых функций)

Таблица §0 неполна. Реальная кодировка эмулятора — две формы:

| Байты | Смысл |
|---|---|
| `CD 34`…`CD 3B` + modrm[+disp] | команда x87 семейства `D8+(vec−0x34)` (CD34→D8, CD35→D9, … CD3B→DF) с **выброшенным** ESC-байтом; modrm и displacement идут сразу за INT |
| `CD 3C` + полный `ESC modrm…` | команда x87 с **сохранённым** ESC-байтом (преобладает в f344/f359/cf98, §0) |
| `CD 3D` | сервис слова статуса x87 (FNSTSW-подобный), обычно перед `SAHF`/`Jcc` |

Пример: `CD 35 EE` — это НЕ «INT 35 + OUT DX,AL», а `D9 EE` = **FLDZ** (байт 0xEE —
modrm без операнда, а не CPU-опкод OUT; «OUT DX,AL» из таблицы §0 — артефакт декодирования
Ghidra, встречающийся у modrm-байтов вида 0xEE/0xF7). Обе формы дают одну команду x87;
выбор формы — за компилятором. Прочие факты адресации, пригодившиеся ниже:

- near-call IP арифметика идёт **mod 0x10000** (вызов из 0x1E91A с rel 0x5278 → цель 0x3B92
  = `FUN_1000_3b92`);
- far-call `9A off seg` в сегмент `0xFF9`-семейства (linear 0xFF90–0xFFFF) — вызов
  TSR-эмулятора/рантайма **вне EXE**: `lcall 0xFFA9`, `lcall 0xFF95` — содержимое
  [НЕИЗВЕСТНО: рантайм не входит в образ].

## 1. f344 — восстановленный алгоритм (псевдокод Python, с адресами)

`FUN_1000_f344` — **драйвер трассировки «ход лучей» (вариант A, основная длина волны)**:
разбор записи запроса из потока ввода, подготовка стартового состояния луча, прогон
(математика — в общем хвосте, см. §4), печать таблицы хода лучей в форматах TABRAY-семейства.

```python
def FUN_1000_f344(param1, count_ptr, rec_buf, ns_ptr, ...):   # 0x1F344
    CH = (in_CX >> 8) & 0xFF
    M[0x50c2] = 0            # 0x1F34E: режим A (флаг трейсера; у f359 = 1)
    M[0x5038] = 0            # 0x1F356: «вторая запись не читалась»

    if M32[ns_ptr] == 0:     # 0x1F36B: пустой счётчик поверхностей
        INT_35h()            # 0x1F373: диагностика эмулятора, выход
    else:
        count = M32[count_ptr]; M32[count_ptr] = count + 1   # 0x1F383: 32-битный инкремент счётчика записей
        SI = count << 2                                   # 0x1F38F: индекс REAL*4-массива
        INT_3Ch()             # 0x1F396

    # --- чтение стартовой точки луча (REAL*8 из потока) ---
    (d) = FLD_m32[BX+SI-4]    # 0x1F398: FLD m32 — чтение REAL*4 записи
    M8[0x505a..0x5061] = D[far_ptr]    # 0x1F3AA: копия REAL*8 (4×MOVSW) во времянку 0x505A
    M8[0x5072..0x5079] = M8[0x505a..0x5061]   # 0x1F3C2: дубль во вторую времянку 0x5072

    flag = byte_at(0x2e96) < CH         # 0x1F4EB: CMP [2E96],CH — сравнение с кодом режима
    rec_buf[SI - 0x33] += ord('=') + flag   # 0x1F4F4(окр.): пометка записи обработанной ('=')

    # --- разбор NS (знаковое число поверхностей) ---
    NS = M32[ns_ptr]
    absNS = abs(NS)                     # 0x1F418-0x1F427: CWD/NEG — |NS|
    if absNS > 100:                     # 0x1F3F0: CMP DI,100 / JG
        FUN_1000_ff52()                 # 0x1FF52: ошибка «слишком много поверхностей»
        return
    if absNS > 2:                       # 0x1F42E: CMP DI,2 / JLE — иначе пропуск блока
        M[0x5038] = 1
        count2 = M32[count_ptr]; M32[count_ptr] = count2 + 1
        if NS < 1:                      # 0x1F428: OR SI,SI / JG — знак NS = тип предмета
            M[0x5036] = -NS - 2         # 0x1F436: MOV AX,SI; NEG AX; SUB AX,2
            last = -NS
        else:
            M[0x5036] = NS // 2 - 1     # 0x1F44C-0x1F457: CWD; SUB AX,DX; SAR AX,1; DEC AX
            last = NS // 2
        M[0x50d4] = last + 1            # индекс плоскости изображения
        M32[count_ptr] += M[0x5036]     # 0x1F461: продвижение указателя записей на шаг

    # --- инициализация истории координат ---
    M[0x5034] = 10
    for w in range(0x20):               # 0x1F47F: REP MOVSW 0x20 слов
        M16[0x3f30 + 2*w] = M16[0x3f28 + 2*w]     # сдвиг блока REAL*8-истории на 1 элемент
    M8[0x3f28..0x3f2f] = M8[0x505a..0x5061]   # 0x1F4A3: X_start (REAL*8)
    M8[0x3f48..0x3f4f] = M8[0x5072..0x5079]   # 0x1F4AB: Y_start
    M8[0x3f68..0x3f6f] = M8[0x5082..0x5089]   # 0x1F4B3: Z_start  (шаг 0x20 междутройками)

    LES BX, [BP+0x22]; INT_3Ch(); FMUL_m64[BX]   # 0x1F4EF-0x1F4F4: st *= параметр REAL*8
    ...INT38-обёртки, FDIVR m32 [BP+DI]          # 0x1F50D: деление (нормировка/Снелл, см. §4)

    # --- копирование стартового состояния в рабочий массив ---
    M[0x5034] = 10
    while M[0x5034] <= 3 or first_pass:           # 0x1F52C-0x1F569
        SI = M[0x5034]; SI <<= 3                  # 0x1F52B-0x1F532: ×8 — индекс REAL*8
        copy_double(0x3BC8 + SI, 0x3EF8 + SI)    # 0x1F535-0x1F542: 4×MOVSW
        M[0x5034] += 1                            # 0x1F560: INC [5034] — переход к след. элементу
        if M[0x5034] > 3: break                   # 0x1F564: CMP [5034],3 / JLE 0x1F52C

    LES BX, [BP+0x22]; INT_3Ch(); FLD_m64[BX]     # 0x1F56B-0x1F570: st = параметр REAL*8
    ...FP-математика общего хвоста (§4): перенос, преломление, цикл по поверхностям ...

    # --- печать таблицы хода лучей ---
    FUN_1000_7df9(...)                            # заголовок таблицы
    for i in range(1, M16[0x33f4] + 1):           # 0x1F9xx: цикл по поверхностям 1..N
        FUN_3000_220d(); FUN_3000_2255(0x2e73, fmt=0x3a3a)   # колонка 1
        func_0x3226d(0x2e73, 0x3a43)              # колонка 2 …
        func_0x325d9(0x2e73, 0x3a48)
        FUN_3000_21a1(0x2e73, 0x3a51)
        func_0x3195 (0x2e73, 0x3a5a)
        func_0x322a3(0x2e73, 0x3a72); func_0x3195(0x2e73, 0x3a7b)
        func_0x322a3(0x2e73, 0x3a93); func_0x3195(0x2e73, 0x3a9c)
        func_0x322a3(0x2e73, 0x3ab4); func_0x3195(0x2e73, 0x3abd)
        func_0x322a3(0x2e73, 0x3ad5)
        i += 1                                    # инкремент цикла поверхностей
    FUN_1000_1333(); func_0x2617a()               # эпилог, RET
```

Форматы `0x3a3a…0x3ad5` (DS-сегмент 5000) — числовые колонки ~8 полей — соответствуют
семейству TABRAY `(1X,i3,4(f9.3,a1),f8.3,f8.3,a1,f9.3,f8.3)` (карта: 0x4d9).
Печатальщики 3000_22xx / 32xxx — те же, что в карте отмечены для FUN_4000_0458.

### Кто вызывает трейсеры (контекст, `FUN_1000_cf98`, linear 0x1CF98)

`FUN_1000_cf98` — оркестратор прогона: цикл по поверхностям со счётчиком `M[0x4386]`,
сохранение/восстановление состояния луча, и **выбор трейсера по флагу длины волны**
(декомпил `1000_cf98_FUN_1000_cf98.c`, стр. 635–672):

```python
if wl_flags[surf*2 - 2] == 0:        # основная длина волны
    FUN_1000_f344(0x4388, ...)       # трейсер A
else:                                # другая длина волны:
    FUN_1000_f359(0x2e73, 0x4388, ...)   # трейсер B
    FUN_1000_e920(...)               # + печать TABOC1 (окулярные/осевые аберрации)
```

Состояние луча у оркестратора — **две тройки REAL*8** (как Ray(x,y,z,k,l,m) порта):
`0x3BC8+i*8` = X,Y,Z; `0x3BE0+i*8` = K,L,M (i=1..3); бэкапы `0x43E6/0x43CA`, рестарт из
`0x43EE/0x3D2`-семейства (декомпил стр. 488–496, 570–585).

## 2. f359 — отличия от f344

Побайтовое сравнение декомпилов (`1000_f344…c` vs `1000_f359…c`, 1248 vs 1247 строк) и
дизассемблера:

1. **f359 — это второй вход ТОЙ ЖЕ функции**, на 21 байт позже: f344 = вход `0x1F344`
   (`MOV [BP-2], 0`), f359 = вход `0x1F359`. Разница входных «подписей» в декомпиле
   (лишний ведущий параметр у f359) — артефакт Ghidra: f344 читает свой первый аргумент
   со сдвигом стека из-за раннего `PUSH`.
2. Единственное содержательное отличие в прологе:
   - f344, `0x1F34E`: `*(undefined2 *)0x50c2 = 0;`
   - f359, `0x1F363`: `*(undefined2 *)0x50c2 = 1;`
   плюс локальный флаг `[BP-2]` = 0 / 1.
3. **Семантика флага `0x50c2`**: выбор ветки внутри общего хвоста — режим B = трассировка
   на другой длине волны (хроматизм). Это подтверждается вызовом из `FUN_1000_cf98`:
   f359 зовётся только когда флаг волны для поверхности ≠ 0, и сразу за ним печатается
   таблица осевых/окулярных хроматических аберраций TABOC1 (`FUN_1000_e920`).
4. В остальном (разбор записи, NS-сплит, история координат, печать) — тела идентичны
   построчно; все различия далее — шум регистровых имён от Ghidra.

То есть «трейсировщик B (вероятно хроматизм)» из карты подтверждается: **это не отдельный
алгоритм, а тот же трейсер с флагом длины волны.**

## 3. Математика трассировки в общем хвосте (0x10C72–0x112D0)

Куски с метками `LAB_1000_0c72/0c9b/0e8b/0fb8/1037/11d2/128b/12cb` — общий хвост, куда
падает управление и из f344, и из cf98. Ниже — расшифрованные формулы (байты→мнемоники,
обёртки INT 3Ch помечены как эмуляция x87).

### Ф1. Перенос координаты (transfer) — `0x1100C–0x11037`

```asm
0x1100C  C4 7E 46      LES  DI,[BP+0x46]      ; адрес массива приращений (REAL*8)
0x1100F  CD 3C         INT  3Ch               ; обёртка x87 (эмулятор)
0x11011  DD 41 F8      FLD  m64 [BX+DI-8]     ; st0 = приращение D[i-1] (REAL*8)
0x11014  8B 5E F4      MOV  BX,[BP-0x0C]      ; j = номер координаты (1..3)
0x11017  8B C3         MOV  AX,BX
0x11019  D1 E3         SHL  BX,1
0x1101B  03 D8         ADD  BX,AX             ; BX = 3*j
0x1101D  8B C6         MOV  AX,SI             ; i = номер луча
0x1101F  D1 E0         SHL  AX,1
0x11021  D1 E0         SHL  AX,1              ; AX = 4*i (элемент REAL*4)
0x11023  03 D8         ADD  BX,AX             ; BX = 3*j + 4*i
0x11025  03 5E 0A      ADD  BX,[BP+0x0A]      ; + база массива координат
0x11028  8E 46 0C      MOV  ES,[BP+0x0C]
0x1102B  2B 5E F8      SUB  BX,[BP-0x08]
0x1102E  CD 3C         INT  3Ch
0x11030  D8 47 0C      FADD m32 ES:[BX+0x0C]  ; координата += приращение
0x11033  CD 3C         INT  3Ch
0x11035  D9 5F 0C      FSTP m32 ES:[BX+0x0C]  ; записать обратно
```

**Формула:** `коорд[i][j] = коорд[i][j](m32) + D[j](m64)` — накопительный перенос; массив
координат — REAL*4 с раскладкой `[i][j]` (шаг 4 на координату, 3 координаты на луч),
приращения — REAL*8. T·D (толщина × косинус) вычисляется раньше (FMUL, см. Ф5) и приходит
в [BX+DI-8] уже умноженным.

### Ф2. Цикл по X,Y,Z с записью координат — `0x10FB4–0x10FFB`

```asm
0x10FB4  C7 06 84 43 01 00   MOV [0x4384],1     ; j = 1
loop_j:                                             ; = LAB_1000_0fb8
0x10FBA  8B 36 84 43         MOV SI,[0x4384]
0x10FBE  B1 03               MOV CL,3
0x10FC0  D3 E6               SHL SI,CL           ; SI = j*8 (индекс REAL*8)
0x10FC2  8B 46 F4            MOV AX,[BP-0x0C]    ; k
0x10FC5  F7 26 84 43         MUL [0x4384]        ; AX = k*j
0x10FC9  8B D8               MOV BX,AX
0x10FCB  C4 7E 72            LES DI,[BP+0x72]
0x10FCE  26 8B 05            MOV AX,ES:[DI]      ; n = число лучей
0x10FD1  D1 E0 / D1 E0       SHL AX,1 ×2         ; 4*n
0x10FD5  03 D8               ADD BX,AX           ; BX = k*j + 4*n
0x10FD7  03 5E 0A            ADD BX,[BP+0x0A]
0x10FDA  8E 46 0C            MOV ES,[BP+0x0C]
0x10FDD  2B 5E F8            SUB BX,[BP-0x08]
0x10FE0–0x10FEC              INT 39/34/38-обёртки: x87-операции + CMP [SI+0x3BE0] (направления K,L,M)
0x10FED  CD 3C / D9 5F 0C    FSTP m32 [BX+0x0C]  ; запись координаты j луча
0x10FF5  FF 06 84 43         INC [0x4384]        ; j++
0x10FF9  83 3E 84 43 03      CMP [0x4384],3
0x10FFE  7E …                JLE loop_j          ; j = 1..3 = X, Y, Z
```

### Ф3. Переход к следующей поверхности: сохранение состояния луча — `0x1109F–0x110D6`

```asm
0x1109F  C7 06 82 43 01 00   MOV [0x4382],1     ; i = 1
loop_i:
0x110A5  8B 36 82 43         MOV SI,[0x4382]
0x110A9  B1 03               MOV CL,3
0x110AB  D3 E6               SHL SI,CL          ; SI = i*8
0x110AD  56                  PUSH SI
0x110AE  8D BC E6 43         LEA DI,[SI+0x43E6]
0x110B2  8D B4 C8 3B         LEA SI,[SI+0x3BC8]
0x110B6  1E 07               PUSH DS / POP ES
0x110B8  A5 A5 A5 A5         MOVSW ×4           ; X,Y,Z: 0x3BC8+i*8 → 0x43E6+i*8
0x110BC  5E                  POP SI
0x110BD  56                  PUSH SI
0x110BE  8D BC CA 43         LEA DI,[SI+0x43CA]
0x110C2  8D B4 E0 3B         LEA SI,[SI+0x3BE0]
0x110C6  A5 A5 A5 A5         MOVSW ×4           ; K,L,M: 0x3BE0+i*8 → 0x43CA+i*8
0x110CA  5E                  POP SI
0x110CB  FF 06 82 43         INC [0x4382]       ; i++
0x110CF  83 3E 82 43 03      CMP [0x4382],3
0x110D4  7E CF               JLE loop_i         ; i = 1..3
```

Дубль этой конструкции в декомпиле оркестратора `FUN_1000_cf98` (стр. 485–498):
`*(undefined2 *)(iVar22 + 0x43e6) = *(undefined2 *)(iVar22 + 0x3bc8);` — т.е. **дек компил
подтверждает байтовую расшифровку**. Счётчик поверхностей — глобал `M[0x4386]`
(`*piVar1 = *piVar1 + 1; … while 0x4386 <= [BP-0x3C]`, стр. 455–458).

### Ф4. Преломление/нормировка — итеративное деление — `0x110D8–0x110FE` (частично)

```asm
0x110D8  CD 39 …             INT 39h            ; эмулятор x87
0x110E0  D8 3B               FDIVR m32 [BP+DI]  ; обратное деление (рабочий массив на стеке)
0x110E5  D8 3B               FDIVR m32 [BP+DI]
0x110F4  CD 39               INT 39h
0x110F6  7E DC               JLE 0x110D4        ; цикл до выполнения условия
0x110F8  CD 3D               INT 3Dh            ; выгрузка статуса x87
0x110FA  8A 66 DD            MOV  AH,[BP-0x23]
0x110FD  9E                  SAHF               ; статус x87 → флаги CPU
0x110FE  74 3B               JE   0x1113B       ; тест условия (знак/сходимость)
0x11100  BF C2 43 / BE 30 3B MOV DI,0x43C2; MOV SI,0x3B30
0x11106  A5 ×4               MOVSW ×4           ; копия REAL*8-константы 0x3B30 → рабочая
```

Пара FDIVR + цикл + SAHF/JE — итеративное деление/уточнение (нормировка вектора направлений
или итерация Снелла). Аналогичный паттерн в теле f344: `0x1F50D FDIVR m32 [BP+DI]`.
[НЕИЗВЕСТНО: 0x110D8–0x110FA — точный порядок операндов внутри INT-обёрток (диспетчеризация
эмулятора не восстановлена); если понадобится точная форма — читать TSR-эмулятор.]

### Ф5. Умножение на параметр REAL*8 (T·D и масштабирования) — f344 `0x1F4EF–0x1F4F4` и хвост `0x1D002–0x1D009`


### Ф6. Разметка массива поверхностей — `0x1CFB2–0x1CFC7` (cf98)

```asm
0x1CFB2  B8 18 00         MOV  AX,0x18
0x1CFB5  F7 2E C2 4D      IMUL [0x4DC2]       ; AX = 0x18 * i — шаг записи = 24 байта
0x1CFB9  8B F0            MOV  SI,AX
0x1CFBB  8B 1E BE 4D      MOV  BX,[0x4DBE]    ; j — счётчик
0x1CFBF  B1 03 / D3 E3    SHL  BX,3           ; BX = j*8
0x1CFC5  80 40 3D 8B      ADD  [BX+SI+0x3D],-0x75   ; поле флага на +0x3D записи
```

(В декомпиле: `pcVar2 = iVar18 + iVar15*0x18 + 0x3d; *pcVar2 += -0x75;` — стр. 86–87.)

## 5. Вердикт

**СОВПАДАЕТ (алгоритм порта воспроизводит OPAL) — по структуре и по местам, где формулы
восстановимы однозначно; с оговорками по точности и форме преломления.**

По пунктам:

1. **Представление луча** — СОВПАДАЕТ: тройки REAL*8 «точка + направление» (0x3BC8/0x3BE0)
   ↔ `Ray(x,y,z,k,l,m)`.
2. **Перенос луча** (Ф1, 0x1100C–0x11037) — СОВПАДАЕТ: накопительное
   `координата += приращение` с произведением T·D (FMUL 0x1F4F4/0x1D007) ↔ `ray.x += t*ray.k`.
   Отличие: OPAL пишет координаты в REAL*4-массив (шаг 4 байта), порт — float64; на длинных
   ходах это даёт разницу округления ~1e-7 отн., для таблиц f9.3 несущественную.
3. **Преломление** (Ф4, 0x110D8–0x110FE, FDIVR×2+SAHF) — ОТЛИЧАЕТСЯ ПО ФОРМЕ, СОВПАДАЕТ ПО
   СМЫСЛУ: OPAL решает деление итеративно (эмулятор x87, цикл с тестом статуса), порт —
   замкнутой векторной формулой Снелла. Прямое побайтовое подтверждение коэффициентов
   n1/n2 недостижимо без реверса TSR-эмулятора [НЕИЗВЕСТНО: 0x110D8–0x110FA]; косвенно
   (совпадение выходных таблиц, см. REVERSE_MAP §сверка) — эквивалентно.
4. **Переход к следующей поверхности** (Ф3, 0x1109F–0x110D6 + счётчики 0x4382/0x4386/0x5034) —
   СОВПАДАЕТ: инкремент счётчика + сохранение состояния ↔ цикл `for surf in surfaces` +
   история `TraceResult`.
5. **Организация «две длины волны»** — СОВПАДАЕТ: f344/f359 = один код с флагом `[0x50c2]`
   (0/1), вызов по флагу волны из cf98 + печать TABOC1 ↔ параметр волны порта + расчёт
   хроматических аберраций.
6. **Таблицы хода лучей** — СОВПАДАЕТ: цикл поверхностей 1..N с ~8 числовыми колонками
   (форматы 0x3a3a…0x3ad5, TABRAY-семейство) ↔ `compute_gauge_rays`/`compute_ray_coordinates`.

Кавычки формул с адресами (мин. 3 по задаче): **перенос** — 0x1100C–0x11037 (Ф1);
**запись X,Y,Z** — 0x10FB4–0x10FFB (Ф2); **переход к след. поверхности** — 0x1109F–0x110D6
(Ф3); **преломление/нормировка** — 0x110D8–0x110FE (Ф4); **T·D** — 0x1F4EF–0x1F4F4,
0x1D002–0x1D009 (Ф5); **разметка поверхностей** — 0x1CFB2–0x1CFC7 (Ф6).

### 7.0. Контекст вызова (`FUN_1000_0746`, декомпил стр. 290–749)

Оркестратор анализа вызывает парные вычислители **по флагу записи `rec+0x6a`**
(стр. 670/674): `FUN_1000_93f3(...)` либо `FUN_1000_9897(...)`. Аргументы 93f3 —
семь far-указателей: `DS:0x3A10`, `rec+0x70`, `rec+0x68`, `rec+0x80`, `rec+0x78`,

(стр. 749) — т.е. вычислители работают с теми же глобальными тройками REAL*8,
что и трейсеры §1.

Глобальное состояние (DS), которым оперирует вся группа:

| Адреса | Смысл |
|---|---|
| `0x3BC8 / 0x3BD0 / 0x3BD8` + `0x3BE0 / 0x3BE8 / 0x3BF0` | тройки REAL*8 состояния луча (§1); `0x3BF8` — 7-й double-делитель (вероятно n: хранятся «оптические косинусы» K·n, L·n, M·n) |
| `0x3B30 / 0x3B38` | пара REAL*8 (cosθ, sinθ) поворота на угол поля |
| `0x3B28` | кривизна текущей поверхности c (входит и в преобразование луча, и в рекурренцию) |
| массив A: база `0x3C58`, записи 3×REAL*8 с шагом 0x18 | «высоты» дифференциального следа (элементы записи j: `0x3C58+0x18j`, `+8`, `+16`) |
| массив B: база `0x3D18`, тот же шаг | «углы/наклоны» дифференциального следа |
| `0x3C20/0x3C28` | аккумуляторы W₁/W₂; `0x3C30+8k` — цепочка аккумулируемых слагаемых |

### 7.1. FUN_1000_9232 (0x19232) — поворот системы на угол поля

`retf 0xC` — 3 far-аргумента: ptr-пара (cos,sin) `[BP+0xE]`, счётчики `[BP+6]/[BP+0xA]`.

```python
def FUN_1000_9232(rot=0x3B30, nA=0x39E0, nB=0x39E0):      # 0x19232
    c, s = D[0x3B30], D[0x3B38]            # (cosθ, sinθ)
    # пара 1 главного луча: 0x19248-0x19277
    t = D[0x3BE0]; D[0x3BE0] = t*c + D[0x3BD8]*s
    D[0x3BD8]               = D[0x3BD8]*c - t*s
    # пара 2: 0x1928A-0x192BC
    t = D[0x3BF8]; D[0x3BF8] = t*c + D[0x3BF0]*s
    D[0x3BF0]               = D[0x3BF0]*c - t*s
    for j in range(1, NS + 1):             # 0x19329-0x193D7 (NS = M32[0x39E0])
        for (a, b) in ((0x3C78 + 0x18*j, 0x3C80 + 0x18*j),    # записи массива A
                       (0x3D38 + 0x18*j, 0x3D40 + 0x18*j)):   # записи массива B
            t = D[b]; D[b] = t*c + D[a]*s
            D[a]        = D[a]*c - t*s
```

Это поворот Гивенса двух REAL*8-пар на угол θ — по одной паре из «координатной» и из
«направляющей» части состояния. Точная привязка адресов `0x3BD8/0x3BE0/0x3BF0/0x3BF8`
к конкретным координатам Y/Z/L/M двусмысленна между раскладкой §1 (тройки
`0x3BC8/0x3BD0/0x3BD8` + `0x3BE0/0x3BE8/0x3BF0`) и порядком загрузки стартового
запуска луча `FUN_1000_9d7a` (`[0x3BD0]=0`; `0x3A90→0x3BD8`; `0x3A98→0x3BE0`;
`[0x3BE8]=[0x3B78]/v`; `[0x3BF0]=[0x3B80]/v+[0x3AA0]`) —
[НЕИЗВЕСТНО: какая раскладка итоговая; на семантику не влияет]. Существенно другое:
**поворот ведётся на угол поля косого пучка**, чтобы в повернутых осях главный луч
стал осевым — тогда для дифференциального следа достаточно плоской 2×2-рекурренции
в меридиональной плоскости (классический приём расчёта астигматизма по Коддингтону).

```python
            out_j = (D[0x3D28 + bx + 0x18*j] - K*D[0x3D40 + 0x18*j]/n) / n
    else:                                      # 0x19BC2-0x19BEF: «рефракция наклона»
        out = (P*n + M) / (n - P*M)
    R4[rec+0x80] = -(D[0x3C70]/D[0x3D30]) * n  # 0x19C15-0x19C2C: Z'm-кандидат (×n, знак −)
    R4[rec+0x78] = -(D[0x3C78]/D[0x3D38]) * n  # 0x19C6C-0x19C83: Z's-кандидат (×n, знак −)
    R4[p6+0]    =  D[0x3C80] / pow(D[0x3D30], D[0x2D8E])      # 0x19C39: как 0x19739
    R4[p5+0]    =  D[0x3C98] / (D[0x3D30]*D[0x3D38]**2)       # 0x19C87: как 0x197CD
    D[0x4BB2]   =  D[0x3D30]                   # 0x19CB5: экспорт знаменателя (u_мер) наружу
    R4[p1+0], R4[p1+4] = ((D[0x3D30] - M*D[0x3D40]/n)/n, D[0x3D38]/n)  # 0x19CC1-0x19CE2
    for k: D[0x3C70 + 0x18*k] /= n; D[0x3D30 + 0x18*k] *= n   # 0x19D10-0x19D23: ОБРАТНЫЙ n-масштаб
    D[0x3C80] = u*(c*D[0x3C70]*M*T**2 + D[0x3C80])            # 0x19D33-0x19D6D: вклад наклона M и толщины T
    D[0x3C98] = u*u*D[0x3C98]
```

Симметрия прямого (0x198A7+) и обратного (0x19D10-0x19D23) n-масштабирования — это
перевод «оптических косинусов» (×n) в истинные и обратно вокруг ядра расчёта; выход
`(L/n, M/n)` в `rec+0x68` — истинные направляющие косинусы главного луча
(тангенс наклона = семейство Tg' таблицы TABGL, см. §7.4).

### 7.4. Что вычисляют 93f3/9897 (геометрический смысл)

Ключ — связка с `FUN_1000_e7db` (0x1E7DB, `retf 4`, 1 far-аргумент = ptr REAL*8 из
`rec+0x26`) — **инициализатором дифференциального следа**:

```python
def FUN_1000_e7db(ptr_r8):                     # 0x1E7DB
    K = K - v                                  # 0x1E80D-0x1E815: FSUBR — возмущение косинуса
    lcall_ff95(0x2E62, 0x4C6)                  # 0x1E82A: TSR [НЕИЗВЕСТНО: 0xFF95]
    K = v + K                                  # 0x1E834-0x1E83B: симметричная конечная разность по K
    if NS < 0:                                 # 0x1E85E-0x1E87B
        D[0x3D48] = D[0x3D50] = const_0x2E6A   #   засев записи j=2 массива B
        NS = -2; M16[0x39E4] = 2
    else:                                      # 0x1E889-0x1E8D0 (NS > 0)
        D[0x3D60] = D[0x3D80] = const          #   засев записи j=4 массива B (e1, e3)
        D[0x3D70] = -L/n; D[0x3D88] = -M/n     #   засев элементов e2/e4 косинусами главного луча
        NS = 4; M16[0x39E4] = 4                #   (знак «−» согласован с h' = −(u + c·h) из §7.2)
    if версия([0x2E72]) > 6:                   # 0x1E8D6-0x1E919
        FUN_1000_3b92()                        #   near-call с IP-wrap mod 0x10000 (§0.1)
```

Т.е. поток данных: **e7db засевает массив B косинусами главного луча → трейсер §1
прогоняет поверхности → 93f3/9897 делят «высоты» A на «углы» B**. Отношение
`h/u` — это осевое расстояние от опорной поверхности до точки пересечения
дифференциального луча с осью, т.е. **астигматический отрезок**. Две независимые
пары элементов (меридиональная `0x3C70/0x3D30`, сагиттальная `0x3C78/0x3D38`) дают
**Z'm и Z's**; их разность — астигматизм. Знак-минус и множитель n у 9897 —
следствие отсчёта в «оптических» (×n) переменных и направления оси.

Разностные выходы `(−D[0x3BF0]) − D[0x3D90+0x18k]` (0x19627-0x1968B) и
`(−M) − D[0x3D90+0x18k]` (0x19848-0x19888) — смещения относительно эталонной записи —
семейство **дисторсии/Tg'** (колонки TABBEA «Дисторсия, %» и TABGL «Tg'*100»);
окончательная привязка колонок — [НЕИЗВЕСТНО: сопоставление полей записи
rec+0x68…0x92 с колонками формата 0xC56 идёт через UI-диспетчер сегмента 4000
(0x495B3-0x495DB), который математики не содержит].

Вспомогательные функции группы:

- **FUN_1000_9d7a** (0x19D7A) — запуск веера лучей: `[0x39D0/0x39D2]=0`; `[0x3BD0]=0`;
  стартовые координаты `0x3A90→0x3BD8`, `0x3A98→0x3BE0`; косинусы `[0x3BE8]=[0x3B78]/v`,
  `[0x3BF0]=[0x3B80]/v+[0x3AA0]`; копии в `0x4BC6/0x4BCE`.
- **FUN_1000_a776** (0x1A776, `retf 8`) — установщик сетки для кода команды 99:
  `NS := 4` либо `−2 / −(N+4)`; `arg1[0]=arg1[8]=const(0x2DA6)` при `arg1 = DS:0x3B98`.

## 8. Каустики (радиусы, %) — формы 2-го порядка 93f3/9897

### 8.1. Восстановленные формулы

Помимо отношений h/u (§7), оба вычислителя выдают две формы 2-го порядка — кандидаты
«Радиусы каустики» из заголовка TABBEA (0xC56: «Дисторсия, Астигмат.отрезки,
Радиусы каустики, Z'm, Z's, %»):

```python
# 93f3:
R4[rec+0x92] = D[0x3C80] / pow(D[0x3D30], D[0x2D8E])       # 0x19739-0x1975F (при [0x39EC]≠0)
R4[rec+0x78] = D[0x3C98] / (D[0x3D30] * D[0x3D38]**2)      # 0x197CD-0x197F7 (при [0x39EC]==2)
D[0x3C80] *= D[p_scale]; D[0x3C98] *= D[p_scale]           # 0x197FB-0x19810: нормировка на выход
# 9897 — те же две формы: 0x19C39-0x19C5F и 0x19C87-0x19CB1
# 9897 — только здесь: домешивание наклона главного луча M и толщины T:
D[0x3C80] = u*(c*D[0x3C70]*M*T**2 + D[0x3C80])             # 0x19D33-0x19D6D
D[0x3C98] = u*u*D[0x3C98]
```

Показатель степени — рабочая переменная `[0x2D8E]` (в образе мусор, значение в неё
кладёт рантайм): по форме знаменателя (квадрат «угла» u при числителе 2-го порядка от
высоты) это квадрат, т.е. `[0x2D8E] ≈ 2.0` — [НЕИЗВЕСТНО: точное значение; рабочий
смысл — знаменатель u², типичный для радиуса кривизны каустики r ≈ h₂/u²-семейство].

Геометрия: `[0x3C80]`/`[0x3C98]` — элемент e3 записи 1 и элемент e3 записи 2 массива
«высот», накапливающие квадратичные члены дифференциального следа; деление на `u²`
(и на `u_t·u_s²` для смешанной формы — селектор `[0x39EC]==2`) даёт **радиус кривизны
каустической поверхности** в меридиональном/сагиттальном сечении, а не положение
фокуса.

### 8.2. Проценты: от чего?

Формат TABBEA `(1x,i2,2f8.5,2F8.5,2f10.3,2f6.3,2f6.1,2(1x,1a,1x,i3))` — пары `2f6.1`
в хвосте: колонки «%». Прямого деления на 100/f′ в восстановленных окнах нет, но есть
единственный множитель нормировки — `D[p_scale]` = `[DS:0x3A10]`, который умножает и
аккумулятор W₂ (0x19435/0x19916), и элементы 2-го порядка на выходе (0x197FB-0x19810).
Согласованность («один масштаб на все относительные выходы») указывает, что
**проценты считаются от одного опорного отрезка, наиболее вероятно — от фокусного
расстояния системы** (гипотеза по подсказке задачи; кто пишет `0x3A10` — вне
исследованных окон) [НЕИЗВЕСТНО: значение и писатель 0x3A10]. Абсолютные колонки
(`2f10.3` — мм-величины) этим масштабом не тронуты — масштабируется только
относительный блок, что подтверждает интерпретацию.

## 9. Хроматизм (TABAX3) — выбор длин волн

### 9.1. Установленный факт: спектральных линий в EXE НЕТ

Побайтовый поиск по всему образу OPALA.EXE (f64 и f32, все вхождения) значений
C/F/d и стандартных линий: `0.58756, 0.65627, 0.48613, 0.5893, 0.5461, 0.4358,
0.6328` (и те же в нанометрах) — **ни одного совпадения** (найдены только
безразличные 1.0 в области литералов 0x51E07-0x54229). Вывод: **OPAL не содержит
встроенной таблицы спектральных линий** — длины волн приходят из пользовательских
данных (записей описания системы), как и показатели преломления.

### 9.2. Механизм второй длины волны

Из §2 и карты cf98: на каждую поверхность есть **флаг длины волны**
(`wl_flags[surf*2-2]`, байт записи 0x18-шага):

```python
if wl_flags[surf*2 - 2] == 0:        # основная длина волны
    FUN_1000_f344(...)               # трейсер A (0x1F344, [0x50c2]=0)
else:                                # другая длина волны:
    FUN_1000_f359(...)               # тот же код, [0x50c2]=1 (0x1F363)
    FUN_1000_e920(...)               # печать TABOC1/TABAX3-семейства
```

Т.е. хроматизм = **повторная трассировка того же луча с другим показателем
преломления** (данными поверхности), с флагом режима в глобале `[0x50c2]`; разности
координат/аберраций между прогонами дают осевые/поперечные хроматические величины.
Формат TABAX3 (DS 0x7af): `(f8.3, f9.2, 5f12.6)` — 7 колонок (длина волны/отрезок +
5 хроматических величин). Сервисный вызов `lcall 0xFF95(DS:0x2E62, DS:0x4C6)` в e7db
(0x1E82A) — рантайм-помощник, вероятно преобразование λ→n —
[НЕИЗВЕСТНО: содержимое TSR-рантайма вне EXE].
