# REVERSE_UNP — полный ре-декомпил распакованного OPALA (EXEPACK снят)

Волна 7 / задача A1. Дополняет `REVERSE_TSR.md` (там §1 — механика EXEPACK, §3 — карта
сегментов, §5 — int 3Fh, §8 — карта памяти). Прежний дамп `decomp_opala` покрывал только
plain-зону файла, импортированную одним блоком на 1000:0000 — far-вызовы не разрешались,
часть RTL была недостижима для автоанализа. Здесь образ пересобран по сегментам с базой 0.

Образ: `analysis/reverse_data/OPALA_unp.bin` (0x5C000 байт, пре-релокационный, load-сегмент 0;
первые байты `55 8B EC` — не MZ). Декомпил: `C:\tools\rea-out\decomp_opala_unp\`
(789 функций × .c + `_index.txt` + `_funcs.txt`), проект Ghidra `C:\tools\rea-out\OPALA_UNP`.

## §1. Заголовок MZ для _unp (пересчёт)

Упакованный OPALA.EXE (0x52F58 байт): pages=0x231, bytes_last=0x172, **nreloc=0**,
hdr_para=0x20, minalloc=0x171D; поля MZ указывают на стаб-распаковщик (CS=0x4464, IP=0x0010,
SS=0x5D0D, SP=0x0080). Оригинальный вход хранит трейлер EXEPACK (file 0x44840, magic `RB`):

| поле | значение | комментарий |
|---|---|---|
| IP0 | 0x9397 | куда LJMP-ит стаб |
| CS0 | 0x2E73 | = начало CODE_RTL2 |
| SP0 | 0x1000 | стек после распаковки |
| SS0 | 0x5B82 | = STACK |
| stub_para | 0x1932 | конец данных стаба |
| mem_end_para | 0x5B79 | граница кучи RTL |

Пересчитанный MZ для образа-результата (если грузить `OPALA_unp.bin` как EXE): **CS=0x2E73,
IP=0x9397, SS=0x5B82, SP=0x1000**, minalloc = 0x5C000-параграфы сверх образа. **Таблица
релокаций пуста и не нужна**: образ получен исполнением стаба при load-сегменте 0
(PSP=0xFFF0, см. `_tools/exepack.py`), все сегментные иммедиаты в коде/данных остались
линк-таймовыми абсолютами (0x0000, 0x0FF9, 0x1F78, 0x2E73, 0x4617, 0x506E, 0x52A6, 0x52D4,
0x552F) — при базе 0 они уже «правильные». Релокации упакованного EXE применяет сам стаб
в рантайме (потому в его MZ и nreloc=0 — таблица упакована в трейлер).

## §2. Карта сегментов и far-скан

Сегменты кода подтверждены гистограммой целей `call far`(9A)/`jmp far`(EA) по образу
(полный список мест — `reverse_data/_unp_fartargets.txt`, 2305 целей в образе):

| сегмент | ссылок | целей | роль |
|---|---|---|---|
| 0x2E73 | 1697 | 120 | CODE_RTL2 — основная часть FORTRAN RTL 5.0 + CRT |
| 0x0FF9 | 122 | 42 | CODE_MATH — математика RTL (x87-обёртки, трансцендентные) |
| 0x1F78 | 77 | 41 | CODE_RTL1 — RTL ч.1 (преобразования, I/O-хелперы) |
| 0x0000 | 42 | 18 | CODE_MAIN — код OPAL |
| 0x46C7, 0x468D | 37 | 12 | far-указатели на строки-константы в DATA_4617 (меню/баннеры) |
| 0x0247, 0x019A и др. | ≤33 | — | **ложные срабатывания**: байты 9A/EA внутри modrm/префиксов (`les bx,[bp-16]` = `26 8B …`, `lea` с modrm 9A) — проверено дизассемблированием окружения |

Блоки Ghidra (скрипт `C:\tools\ghidra_scripts\BuildUnp.java`, лог
`C:\tools\rea-out\decomp_opala_unp_build.log`; адресация — истинные (seg,0), чтобы far-imm
разрешались):

| блок | сегмент | лин. | размер | | блок | сегмент | размер |
|---|---|---|---|---|---|---|---|
| CODE_MAIN | 0000 | 0x00000 | 0xFF90 | | DATA_4617 | 4617 | 0xA570 |
| CODE_MATH | 0FF9 | 0x0FF90 | 0xF7F0 | | DATA_506E | 506E | 0x2380 |
| CODE_RTL1 | 1F78 | 0x1F780 | 0xEFB0 | | DATA_52A6 | 52A6 | 0x02E0 |
| CODE_RTL2 | 2E73 | 0x2E730 | 0x10000 | | DATA_52D4 | 52D4 | 0x25B0 |
| RTL_TAIL | 3E73 | 0x3E730 | 0x0ED0 | | DGROUP | 552F | 0x6530 |
| OVERLAY | 3F60 | 0x3F600 | 0x6B70 | uninit | STACK | 5B82 | 0x07E0 |

OVERLAY неинициализирован намеренно: в рантайме туда int 3Fh-менеджер (REVERSE_TSR §5)
грузит оверлеи; в статическом образе зона 0x3F600..0x46170 нулевая.

## §3. Диф-карта против прежнего plain-декомпила

Соответствие адресов: старый блок 1000:0000 (лин. 0x10000) ↔ новый база 0 ⇒
`old_linear = new_linear + 0x10000` (проверено побайтово: bytes[0..0x3F600) == файлу,
в старый проект файл импортировался тоже без релокаций — потому функции совпали хэшами).

Прогон `_funcs.txt` обоих проектов (ListFuncs.java: entry|name|size|ninsn|md5(мнемоники)),
диффер `_tools/unp_diff.py` → `reverse_data/_unp_diff.txt`:

| метрика | значение |
|---|---|
| функций в старом / новом | 903 / 789 |
| старых в plain-зоне | 891 |
| **идентичны (md5+size)** | **602** |
| изменены (границы/слияние) | 94 |
| отсутствуют по точному входу | 195, из них 156 перекрываются телом новой функции (то же тело, иная граница/слияние) |
| покрытие кода plain-зоны | 0x2CF86 (75.2%) → 0x2E488 (76.5%) |

Причина расхождений не «другие байты», а лучший граф потока: с посегментными блоками
far-вызовы разрешаются, и Ghidra сливает прежние куски (пример: 1000:1333 1925→3541 байт,
1000:3b99 3782→8490; обратные случаи — 39 старых функций вне новых тел, пограничные/
недостижимые регионы, их декомпил остался доступен в старом дампе).

**Новых функций (нет аналога в старом): 93** — см. §4.

## §4. Классификация новых функций

По кластерам (полный список с размерами — `_unp_diff.txt`):

- **CRT-стартап (2E73:9319–95BB), 10 ф.** Вход `2e73_9397_entry` (81 байт): INT 21h
  (проверка версии DOS ≥2), сохранение argv/env в DGROUP+0x2112, вызов 93ea (C-init) и
  3eee (main). Плюс 9319/9335/9351, 9566/956c/95bb — exit/выходные пути.
- **x87-обёртки линкера (2E73:3B91–3EA9), ~28 ф.** Прото-`int 34h..3Dh`: стабы 5–13 байт
  (`push bp; mov bp,sp; int 3Ch; …; retf` — байты `55 8B EC CD 3C … CB` на 2e73:3b91;
  диспетчеры `mov dx,imm; jmp` на 3e43). Именно их зовёт e920 (см. §6): 3a65×14, 3a71×12,
  3b73×10, 3beb×9, 3bfa×5, 3b64×4, 3af5×4 — арифметика над ячейками таблиц.
- **Математика RTL (0FF9), 10 ф.** Гигант 0ff9:05e4 (5492 байта — ядро трансцендентных),
  6ee9 (3867), 32ef, 2ecc, 213a, 3130/3150; 0005/0019 — корневые x87-хелперы (сидированы).
- **RTL ч.1 (1F78), 7 ф.** 6eb0 (2262 — I/O-конвертация), 4332, 1342, 7dea, хвост edb2/ee91/eed9.
- **RTL2 разное (2E73), ~20 ф.** FORTRAN I/O: a6ad (открытие/OPEN — рядом в DGROUP таблицы
  SEQUENTIAL/DIRECT/…), aa63 (формат-парсер стейтментов), ac4e, b07f/b446/b6c8, 8c74, 7764,
  74ec, 9cc0 и пр. — строки ошибок R6000–R6009 и MATH-тексты указывают на диагностику.
- **Код OPAL, недостижимый для старого анализа, 2 ф.:**
  - `0000:0000` (203 байта) — **инициализатор главного модуля**: пролог FORTRAN-main, пишет
    DGROUP-переменные, пушит дальние указатели на данные меню/баннера (DS:0xA2, DS:0x4378,
    DS:0x42FC, DS:0x430A, DS:0x4304) и зовёт драйвер. В старом дампе отсутствовал вовсе.
  - `0000:2558` (5690 байт, 2034 инс.) — крупнейший слитый драйвер (старый аналог 1000:25b0
    имел границу на 0x58 ниже);
- **Хук в данных (52D4:2540), 1 ф.** 46 байт по адресу 0x55280 внутри DATA_52D4: `cli; push bp;
  mov bp,sp; … mov ah,0Ch; mov al,09; int 21h` (буферизованный вывод строки DOS), `mov ah,0;
  int 16h` (опрос клавиши), запись символов по far-параметрам [bp+0Eh]/[bp+0Ah]/[bp+06h],
  `retf 0Ch`. Реальный код, вызываемый по указателю (форматник зовёт через `[0x18dc]`).

Оверлейный менеджер (int 3Fh, REVERSE_TSR §5): диспетчер 2e73:9272 сидирован в BuildUnp
(дизассемблирован), но автоанализ не выделил его в отдельную функцию ни здесь, ни в старом
дампе — обработчик размазан по общему RTL-коду; его разбор остаётся за волной оверлеев.

## §5. Сегменты данных (полный дамп — `reverse_data/_unp_data.txt`)

- **DATA_4617 (0x46170..0x506E0)** — весь «экранный» текст OPAL: главное меню
  «1. Задание режимов расчета габаритов / 2. Параксиальные характеристики / … 9. Заместить
  габариты», командная строка `PAR ZD BS PR AX OF TR REP`, баннер «Cистема-…Работа-…OPAL-PC»,
  статусы «Определяются габариты осевого пучка…», заголовки зон. На строки ссылаются
  far-указатели с сегментами 0x46C7/0x468D (§2).
- **DATA_506E (0x506E0..0x52A60)** — не чистый BSS (уточнение REVERSE_TSR §3): линейная
  часть 0x506E0..0x52420 нулевая (BSS), но остров 0x52420..0x52984 инициализирован —
  word-таблицы-реквизиты форм (на них указывают дескрипторы форматника, §6) и диалог
  «ПАРАМЕТРЫ ФИКТИВНОЙ СИСТЕМЫ» (DZ=, KFK, NKF,KF(I)=H, NDF,DF(I)=H, CVGKDF).
- **DATA_52A6 (0x52A60..0x52D40)** — словарь режимов фикс. ширины (НЕТ/ДА … по Апертуре).
- **DATA_52D4 (0x52D40..0x552F0)** — пул форматных строк и шаблонов форм: 12 именованных
  форматов `*sumsed('( ',I3,5(F11.5),2F10.5)`, `*sumab3`, `*TABRAY`, `*TABOC1`, `*TABOC2`,
  `*TABAX3`, `*TABSAG`, `*TABGL`, `*TABPR2`, `*TABBEA`, `*TABESB`, `*TABEAP` + `*ybbipr`;
  полные заголовки колонок; все «**Ошибка**/*Внимание*»; в хвосте — хук 52d4:2540 (§4).
- **DGROUP (0x552F0..0x5B820)** — данные RTL+OPAL: подпись «MS Run-Time Library - Copyright
  (c) 1989, Microsoft Corp»; имена файлов PROTOCOL.PRN / OPALGRPH.EXE / OPALPCX.EXE / OH.EXE /
  MONITOR.OH / PRINTER.REG / NOTPRINTER.REG / file2prn.ini; команды меню
  'MenuViewEditCalcHelpComm'/'HELP? RESTFULLPRN EXITPROTSAVELOAD'; таблицы OPEN/INQUIRE-
  параметров (SEQUENTIAL/DIRECT/APPEND/…); имена интринтиков FORTRAN (sqrt…tanh) с
  дескрипторами; строки ошибок R6000–R6009; 'opala.exe', 'This program must be run under
  OPAL-PC'; таблица соответствий таблиц `TABESB TABRAY / TABPR2 TABGL TABEAP 22 TABBEA /
  TABOC2 TABOC1 / TABAX3 TABSAG` (диспетчер печати!); заголовки величин с юнитами
  «(гр.мнсек)(дптр)(мм)(дптр**2)(дл. волн)(%)…»; FP-константы.

## §6. Форматник 0x2E73:0x2042 — обзор (детали → TASK_FMT.md)

`FUN_2e73_2042` (129 байт, 51 инс., хэш идентичен старому 4000:0772):

- **Вход**: variadic — 1-й аргумент = near-указатель (DS=DGROUP) на вызывную запись
  дескриптора формата, далее значения списка I/O. **Выход**: слово статуса, 0 = успех
  (все вызывающие проверяют `== 0`).
- Тело: `4e4e` (36 байт — инициализация) → пишет дескриптор в DGROUP+0x1884, список значений
  в +0x1886 → `8e3a(0x18ac)` (42 байта — диспетчер через таблицу методов на +0x18ac) → при
  ошибке `5382`/`56e6`/`4aa0` (диагностика/консоль) → косвенный вызов через `[0x18dc]`
  (хук вывода, §4) → `25f2` (190 байт — завершение записи).
- **Таблицы форматов**: вызывные записи в DGROUP — `+0x1d4, +0x1e8, +0x1fc` (из 0000:67ef),
  `+0x234, +0x244` (из 0000:7514), `+0x5da` (0ff9:86a6), `+0xd6a, +0xd76` (1f78:1f32);
  записи содержат ссылки на сегмент 0x506E (word-таблицы-реквизиты, §5). Сами тексты форматов
  (именованные `*sumsed`…`*TABEAP`) лежат в DATA_52D4.
- **Вызов из e920 — прямо НЕТ**: e920 (диспетчер таблиц, 939 байт) только вычисляет значения
  ячеек через x87-обёртки (3a65/3a71/3b73/3beb/3bfa/…). Печать идёт `65b1 → 67ef/7514 →
  2042` (12 файлов-вызывателей всего; прочие — внутренние повторы RTL: 0ff9:cf7b/e0ca/e19b/
  e943/eb7a, 1f78:2693/e44e).

## §7. Верификация

- **bytes**: образ[0..0x3F600) == файлу OPALA.EXE[0x200..) — 0 несовпадений (unp_map.py).
- **контрольные функции** (md5 мнемоник + размер, старый↔новый):
  - `f344` (1000:0344↔0000:0344) — **идентичен**
  - `f359` (1000:0359↔0000:0359) — **идентичен**
  - `93f3` (1000:93f3↔0000:93f3) — **идентичен**
  - `9897` (1000:9897↔0000:9897) — **идентичен**
  - `0746` (1000:0746↔0000:0746, 2871 байт) — **идентичен**
  - `e920` — 941→939 байт (сдвиг границы на 2, тело то же)
  - форматник `2e73:2042` ↔ старый `4000:0772` — md5 `0539c756…` совпадает полностью.
- **итог**: 602/891 старых функций совпали до хэша — карта адресов и методика верны;
  расхождения объяснимы слиянием по far-рёбрам (§3).
